# Apple SpeechTranscriber Through a Swift C-ABI Bridge

Slugtale reaches macOS 26's `SpeechAnalyzer` / `SpeechTranscriber` through a small Swift static library with a C ABI (`src-tauri/swift/SlugtaleAppleSpeech.swift`), compiled by `build.rs` and linked into the Rust binary behind the `apple-speech-runtime` feature. There is no Rust-only route: unlike the legacy `SFSpeechRecognizer`, the macOS 26 API is Swift-only and is not exported to Objective-C, so the `objc2-speech` crate cannot see it. The bridge is the narrowest surface that works — five C functions carrying nothing but `Int32`, `Double`, and `malloc`-owned strings — and it costs the build a Swift toolchain, which is why the whole thing is opt-in at build time and why every Apple call sits behind `cfg(target_os = "macos")` as well as the feature. The Linux and Windows builds keep the provider type, so Settings can explain the engine's absence, and drop every line that would need Swift.

This engine is the one Slugtale does not own. Apple installs, stores, and updates the speech assets; Slugtale never extracts, bundles, or redistributes them, never uses their output to train or improve another model, and asks for an install only from an explicit user action in Settings. It also never falls back to a server: `SpeechAnalyzer` has no remote mode to misconfigure, and the bridge additionally refuses to transcribe unless macOS reports the locale's assets as installed, so a half-provisioned machine reports itself unavailable rather than reaching for anything else. Measured on macOS 26.5 with all network access denied by `sandbox-exec`, a full transcription still succeeds.
